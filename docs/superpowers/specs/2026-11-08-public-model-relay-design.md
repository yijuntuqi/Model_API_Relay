# 零成本公开模型中转站设计

## 目标与背景

张异希望以零新增费用启动一个面向中国大陆用户的公开模型中转站。第一版用于验证完整业务流程，不承诺生产级稳定性；如果既有测试服务器、Supabase 免费项目或网络连通性不满足要求，后续再迁移。

用户已经确认：允许任何人注册，新用户不赠送调用额度；用户通过微信或支付宝收款码付款，管理员人工确认到账并调整站内额度；首个上游只接阿里百炼的一个模型。

## 第一版范围

- 用户注册、登录和创建自己的下游 API 令牌。
- 新用户注册后不自动获得免费调用额度。
- 管理员配置一个阿里百炼上游渠道和一个模型。
- 用户通过 OpenAI 兼容接口调用该模型，支持普通与流式响应。
- 按上游实际价格配置 New API 的模型计费规则，并核对用量和扣费。
- 展示微信、支付宝收款码及人工充值说明。
- 管理员确认付款后，在 New API 后台调整对应用户额度。
- 保存用户、令牌、用量日志和余额数据，应用重启后不得丢失。
- 当前仅通过本机 SSH 隧道进行私有测试；公网 HTTPS 是公开访问前的强制门槛，自定义域名不是第一版必需项。

## 非目标

- 自动支付、支付回调、退款和发票。
- 注册赠送额度、邀请奖励或无限免费调用。
- 多上游、多模型、负载均衡和自动故障切换。
- Redis、多节点、高可用和独立定制前端。
- 将本机 Ollama 暴露为云端上游。
- 承诺既有服务器或 Supabase 免费项目的可用性、中国大陆访问速度或长期免费额度。
- 在测试服务器部署 Docker、修改 Nginx 或安装系统服务。

## 反目标

即使技术流程能够运行，出现以下情况也不能视为可公开收费运营：

- 上游条款不允许当前转售或再分发方式。
- 用户可以无余额调用、超额扣费或通过重复注册获得资源。
- 上游密钥出现在前端、Git、构建日志或公开环境变量中。
- 管理员无法核对实际 Token 用量、上游费用和站内扣费。
- 数据库随应用重启或重新部署而丢失。
- 未提供内容安全、滥用处置、令牌吊销和用户封禁机制。
- 未配置公网 HTTPS 就公开站点或接受真实付款。

## 技术方案

### 应用

使用 New API 的单体 Web 应用，包含管理界面、用户界面和 API 网关。固定官方 `calciumion/new-api:v1.0.0-rc.49` 镜像版本，从该镜像提取静态 Linux 二进制在测试服务器运行，不使用会自动升级的 `latest`。

第一版不单独开发或部署 Netlify 前端。New API 的“充值链接”可以指向一个人工充值说明页；在需要独立页面时，可使用 Netlify 静态页面展示收款码，但它不参与鉴权、支付确认或 API 转发。

### 托管

- 使用智慧学堂测试服务器，用户严格限定只能修改 `/root/zhangyi`。
- 服务器没有 Docker，且官方独立 Release 二进制因服务器 glibc 过旧而无法运行；最终从本机官方固定版本镜像提取静态 Linux 二进制，上传至 `/root/zhangyi` 并作为私有进程运行。
- 进程使用私有 `3100` 端口；公网 `3100` 不通，当前只通过本机 SSH 隧道访问。
- 已通过 SSH 隧道验证 `/api/status` 返回 success、版本正确、`setup=true` 和 `self_use_mode=false`，Root 管理员已初始化。
- 私有阶段设置 `SESSION_COOKIE_SECURE=false`；`TRUSTED_PROXIES` 尚未配置且启动时存在警告，公网 HTTPS 和可信代理配置均为公开前门槛。
- 当前未配置公网 HTTPS，未修改 Nginx 或系统服务；公开前必须另行获得授权并配置公网 HTTPS，在此之前保持私有。
- 中国大陆连通性需要在公网 HTTPS 就绪后实测；不成功时停止公开推广，而不是假定服务器一定可用。

Railway 不作为第一版长期托管方案：其免费试用和后续额度不足以视为可靠的长期零成本服务。ModelScope Docker 创空间不作为 API 网关方案：其保留 `Authorization` 请求头的要求与 OpenAI 兼容鉴权冲突，且免费资源有时限。

### 数据库

- 使用既有的独立 Supabase Free PostgreSQL 项目，不与其他站点共用数据库。
- New API 通过 `SQL_DSN` 连接 Supabase，使用适合服务器网络条件的连接池地址和 TLS。
- 不配置 Redis；单实例使用 New API 的本地缓存和限流能力。
- 接受 Supabase 免费项目低活跃后可能暂停的限制。
- 部署后验证私有进程重启持久化；公开收费前形成可执行的数据库导出和恢复步骤。

### 上游

- 仅配置用户明确指定的阿里百炼账户。
- 凭据来源为 `D:\secure\ali-api-zy.csv`，实施时只读取所需字段，不在文档、聊天回复、代码或 Git 中复制密钥。
- 从该账户可用模型中选择一个进行首发。
- 上游密钥只进入 `/root/zhangyi` 内的服务端私密配置或 New API 服务端渠道配置。
- 公开收费前确认阿里百炼的服务条款、额度、价格和允许的使用方式。

### 注册与防滥用

- 测试部署初期不公开传播地址。
- 新用户额度固定为零，不生成无额度限制的默认令牌。
- 公开前启用 New API 支持的邮箱验证和人机验证；具体 SMTP 与人机验证配置在实施阶段确认。
- 配置全站 Web/API 限流、单用户额度和可用模型范围。
- 管理员可以封禁用户并吊销令牌。
- 第一版内容安全采用“阿里百炼上游审核 + 管理处置”：依赖上游已有的内容安全能力，由管理员负责投诉处理、滥用核查、用户封禁和令牌吊销，不新增独立内容审核服务。若上游能力不足以满足公开运营要求，则暂停公开，而不是默认继续收费。
- 默认不记录完整提示词、响应正文或 `Authorization` 请求头。

### 人工充值

1. 用户登录后进入充值说明页，查看微信或支付宝收款码、金额与站内额度的对应规则及管理员联系方式。
2. 用户线下付款，并通过说明页列出的方式提供其站点账号和付款信息。
3. 管理员在支付平台确认真实到账，不能仅凭截图入账。
4. 管理员在 New API 后台调整对应用户额度，并保留人工操作记录。
5. 用户检查余额后创建或使用自己的下游令牌。

第一版没有自动订单匹配，也不承诺即时到账。收款码和联系方式由用户后续提供，不进入 Git；如静态托管必须公开图片，则只上传专门用于该站点的收款码。

## 安全与密钥管理

- 管理员使用独立强密码，不与任何现有密码复用。
- `SESSION_SECRET`、`CRYPTO_SECRET`、数据库连接串和上游密钥不得进入 Git；服务器侧私密配置只能放在 `/root/zhangyi` 内。
- 仓库提供不含真实值的配置模板和部署配置。
- 项目 MCP 是可选的账户连接方式，只在确定平台、获得用户确认后配置；令牌不得写入会提交到 Git 的文件。
- 不使用 `all_备注.txt` 中其他个人或第三方的 API 密钥。
- 固定版本并记录升级方式；升级前备份数据库。

## 验收流程

1. 通过本机 SSH 隧道打开私有测试服务，完成管理员初始化并确认普通用户无法进入管理功能。
2. 注册新用户，确认初始额度为零，未充值时调用被拒绝。
3. 管理员配置一个百炼渠道，后台渠道测试成功。
4. 管理员给测试用户增加小额测试额度，创建下游令牌。
5. 使用下游令牌完成一次非流式和一次流式模型调用，确认上游密钥未暴露。
6. 对照 New API 日志、用户余额和百炼用量，检查模型价格、输入/输出 Token 和扣费是否一致。
7. 测试余额不足、错误令牌、被吊销令牌和不可用模型的拒绝行为。
8. 重启 `/root/zhangyi` 内的私有进程，确认用户、余额、令牌和日志仍然存在。
9. 检查收款说明、人工调额和用户看到余额更新的完整流程；测试阶段不发生真实付款。
10. 公网 HTTPS 配置完成后，从不同中国大陆网络实际访问并调用，记录延迟和失败情况。

只有上述关键流程通过，公网 HTTPS 已配置，且条款、内容安全和防滥用事项已处理，才向他人公开地址或接受真实付款。

## 已确认的限制与取舍

- 零成本指第一版不新增托管和数据库费用，不代表模型调用永久免费。
- 既有测试服务器和 Supabase 免费项目只用于当前验证，不提供稳定性承诺。
- 服务器只能修改 `/root/zhangyi`，因此当前使用私有进程而非 Docker、Nginx 或系统服务。
- 人工充值降低开发复杂度，但要求管理员逐笔确认并承担对账责任。
- 第一版只支持一个上游、一个模型，暂不追求完整模型生态。

## 实施时需要补充的材料

- 用户选择的百炼模型及该账户允许用于测试的凭据。
- 测试服务器与 Supabase 的既有授权；Netlify 仅在选择独立静态充值页时需要。
- 公开前的公网 HTTPS 方案及相应授权。
- 站点名称、管理员联系方式、收款码和充值规则。
- 公开注册前所需的 SMTP 与人机验证配置。
